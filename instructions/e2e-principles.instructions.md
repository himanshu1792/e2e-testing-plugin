# E2E Testing Principles

These rules apply across **all phases** of the E2E testing workflow (Analyst, Scenario Writer, Script Writer, Reviewer, Report Generator). They are loaded into every Copilot agent request in any workspace.

## Test design

- **Atomic scenarios.** One scenario = one user flow with one observable outcome. Do not bundle multiple flows.
- **Independent specs.** Each `.spec.ts` must be runnable in isolation. No shared state across files. No depending-on-test-order.
- **Self-cleaning.** Tests that create data must clean it up (or the storage must be ephemeral, e.g., a fresh test account per run).
- **Traceability.** Every scenario references at least one AC number from the story. Every test name embeds the AC: `'AC#3: <scenario title>'`.

## Locator strategy (priority order)

1. **`getByRole('button', { name: 'Submit' })`** — semantic, a11y-friendly. Default choice.
2. **`getByLabel('Email')`** — for form fields with associated labels.
3. **`getByTestId('checkout-button')`** — when the app exposes stable test IDs. Ask the dev team to add them when missing.
4. **`getByText('Exact text')`** — only for static, user-visible content that won't change with i18n or A/B tests.
5. **CSS / XPath** — last resort. Document why in a comment.

When discovering locators, prefer the **Playwright MCP**: `browser_snapshot` to see the accessibility tree, `browser_generate_locator` to mint the locator.

## Waits and assertions

- **Banned:** `page.waitForTimeout(N)`, `await new Promise(r => setTimeout(r, N))`, sleep loops.
- **Use Playwright's auto-waiting:** `await expect(locator).toBeVisible()` waits up to the configured timeout.
- **For navigation:** `await page.waitForURL(predicate)` — never `waitForTimeout`.
- **For network:** `await page.waitForResponse(predicate)` against a real predicate (URL match + status), not arbitrary delays.
- **Bare `if (await locator.isVisible())` is banned.** Use `await expect(locator).toBeVisible()` which auto-waits and asserts.

## Credentials and configuration

- **All env-driven values come from `process.env`.** Specifically:
  - `process.env.APP_URL` — base URL of the app under test
  - `process.env.TEST_USERNAME` — test account username
  - `process.env.TEST_PASSWORD` — test account password
- **Never hardcode credentials** in `.spec.ts`, `.ts`, `.json`, or `.md` files.
- **Never log credential values** — not in `console.log`, not in report files, not anywhere.
- The workspace's `playwright.config.ts` must `import 'dotenv/config'` at the top and set `use.baseURL: process.env.APP_URL`.

## File layout (in the user's per-project workspace)

```
<their-project>/
├── .env                              # APP_URL, TEST_USERNAME, TEST_PASSWORD (gitignored)
├── playwright.config.ts              # loads dotenv, sets baseURL from env
├── package.json                      # @playwright/test
├── tests/                            # specs generated by this framework
│   ├── <story-id>-<slug>.spec.ts
│   └── pages/                        # Page Objects, only if 3+ specs share a flow
│       └── <PageName>.ts
├── test-results/                     # Playwright's default — traces, videos, screenshots
└── test-runs/                        # markdown reports generated by Phase 5
    └── <timestamp>/report.md
```

## Flake handling

- **Hard cap: 3 iterations per spec** in the Reviewer phase.
- After 3 failed iterations, **quarantine** with `test.fixme()` and a comment explaining what's flaky and what's needed to unquarantine (typically: a `data-testid` from the dev team).
- **Never `test.skip()` to hide a failure.** That's silent loss.
- **Never lower an assertion to pass.** If the AC says "user sees X", the test asserts X. If the app shows Y, that's an app bug, file it.

## Agent boundaries

- Each phase has a single, narrow job. Do not try to do the next phase's work.
- Phase transitions happen through **handoff buttons** in chat. Tell the user what the button does.
- If you (an agent) discover you need something the previous phase didn't provide, ask the user — don't silently fabricate it.

## Tone

- Be terse. Don't recap what's already on screen.
- Use chat for human-readable summaries, not for verbatim story dumps.
- Ask focused questions (1–3), not barrages.
